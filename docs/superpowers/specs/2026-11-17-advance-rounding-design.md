# 代垫凑整回款方案（已确认实施）

日期：2026-11-17。用户要求：方案分析沿用当前模型和思考等级；代码开发及修改实施使用 GPT-6.1 Terra。维护者已选择“采用自动拆分，凑整差额计其他收入”，本轮不实施待退款负债流程。

## 问题与根因

用户代垫18.99元，朋友实际转20元。当前 collect 将 amount_cents 同时视为实际收款和核销本金，超过 remaining_cents 即拒绝；detail 也直接合计 collection.amount_cents 计算已收本金。因此当前只能登记18.99元回本，再单独录入1.01元收入，操作割裂。

代码证据：src/lib/advances.js 的 collect/detail/reverseCollection/restoreCollection；src/lib/advance-schema.js 的 advance_collections；src/views/advance-detail.ejs 回款输入及余额说明。现有回款只有一个 transfer 流水关联，撤销恢复和现金流计笔也按这一假设实现。

## 推荐：一张实际到账单，自动拆分回本与凑整差额

日常仍只输入实际到账金额及收款账户。例如输入20元，服务端按整数分计算：本次回本18.99元、凑整差额1.01元、剩余待收0。仅超过待收金额时就地展开差额处理，用户明确选择“朋友凑整，多出的计结算差额收入”，保存前清楚预览三者。

| 指标 | 该例结果 |
|---|---:|
| 实际到账 / 资金流入 | 20.00元 |
| 冲减代垫应收本金 | 18.99元 |
| 其他收入中的凑整差额 | 1.01元 |
| 本次新增个人消费 | 0.00元 |
| 剩余待收本金 | 0.00元 |

朋友明确不用退的1.01元是实际收益。优化是同一回款自动拆分和关联，用户不必手动再记第二笔；不能把20元全计收入，也不能多冲本金形成负应收或把原来的消费金额改掉。

备选（本轮不实施）：如多给的钱需要退还，应作为待退往来款，到账计资金流入、差额形成应付款，实际退回再结清，不先计收入。这个方案适用于误转/暂收，涉及后续退还操作；与明确赠与的凑整收益含义不同。不能仅凭超额金额替用户推断是哪一种。维护者已确认本轮采用明确凑整收益自动拆分方案。

## 交互与数据口径

- 小于待收：保持部分回款，大于0即可，余款继续待收；等额回款按原流程，无额外确认项。
- 超过待收：显示“到账20 / 回本18.99 / 多出1.01”，显式确认差额性质。没有确认的网页或API请求不能静默记收入。数额大小不用于猜测赠与性质。
- 推荐方案差额使用现有 income 语义，显示“凑整差额”，归入已选择的有效收入分类；默认匹配当前账本有效“其他收入”，没有适用分类时保持未分类并如实显示，不复活已删除分类或强造分类。原消费和预算金额不变。
- 一张回款详情同时展示实收、回本、差额；普通账单按一笔实际到账展示总额，收入筛选/报表可查差额分项，账户明细保留真实资金分项。
- 多次回款分别拆分。例如先收10元，再收10元，第二次回本8.99元、差额1.01元，累计实收20元、累计回本18.99元。已结清对象不借此入口随意追加一笔无本金的收入。
- 本金的累计已收与实收累计分开，待收永远只减核销本金。现有 received_cents 的本金含义保持；新增实际到账累计与差额累计明确命名。
- 跨月回款时，到账计回款日资金流，仅差额计回款日收入；原付款月的消费、信用卡原消费总额均不被改写。

## 实施边界（交给 GPT-6.1 Terra）

优先复用 advances 公共服务、现有 transfer/income 流水与原始回款API，不新增通用结算引擎。

1. collection 记录区分实际到账、本金、差额，关联本金转账及差额收入；旧记录迁移为本金=原金额、差额=0。字段最终命名在实施计划中统一，API响应及两份技能同步。
2. collect 在同一事务创建两分项，并保留同一收款账户、发生日/时刻、业务来源和稳定 operation_key。本金转账18.99、收入1.01合计只入账20。新差额处理参数与收入分类纳入幂等签名；旧客户端未显式同意差额处理仍保持超额拒绝。
3. 撤销/恢复整体处理两份分项；恢复容量只检查本金，不拿实收20去与本金18.99比较；任一分项不能从普通交易/报销/其他关联接口独立修改、删除或复活。
4. 现金流按每次 collection ID 去重计一笔到账，不能因为两分项计成两次收款；多次回款各计一笔。消费收入汇总只计算差额，不把本金重复计入。
5. 网页、原生无JS、API确认、错误回显、账单列表/金额排序筛选/详情、账户明细、导出、报表、Agent技能采用相同定义。若导出为原始资金分项须明确，不把拆分分项当两次银行实际到账。
6. 本轮仅覆盖经明确确认的凑整收益，待退款未纳入；少收减免、跨对象预存及多人AA不纳入默认实施范围。若需要待退模式，应先补全负债、退回及撤销恢复闭环再上线，不能只增加一枚无资金效果的标签。

## 成功标准与验证

成功标准：代垫18.99实收20一次完成，收款账户增加20、应收减少18.99至0、消费不变、收入只增加1.01；同key重试无重复，撤销恢复完整且报表不重复计笔。

回归至少覆盖：等额18.99、部分10、实收20、分次10+10、跨月收款、未知/已知时刻、超额未确认拒绝、错误收入分类、同key变参拒绝、事务失败回滚、撤销/恢复、受保护分项、历史回款兼容、收入筛选及现金流一笔计数。金额计算使用服务端整数分，不使用浮点差额。浏览器检查390/1920明暗与JS/无JS实际任务，并运行当前全部业务套件及静态自检；按既有规则独立审查、CI通过后合并main，不发标签或镜像。
